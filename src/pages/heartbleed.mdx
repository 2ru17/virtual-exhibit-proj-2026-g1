# The Heartbleed Bug (CVE-2014-0160)

_When the Internet's heart started bleeding secrets._

On April 7, 2014, the cybersecurity world changed when CVE-2014-0160 was disclosed: a critical flaw in OpenSSL's TLS heartbeat extension that let attackers read up to 64 KB of server memory per request. Private keys, session tokens, passwords, and other sensitive data could leak without leaving clear traces in logs.

Heartbleed is a canonical case study in how a single missing validation check can compromise encrypted communications at Internet scale. This exhibit walks through the vulnerable heartbeat design, shows how the attack worked, and traces the response that followed.

## Stage 1: Healthy Server Heart

The TLS heartbeat extension was designed as a lightweight keep-alive mechanism - a simple "ping" between client and server to maintain an active connection without the overhead of renegotiating cryptographic parameters. In a properly functioning implementation, a client sends a heartbeat request containing a payload and a length field, and the server echoes back exactly what was sent.

The heart pulses rhythmically to simulate a live TLS heartbeat exchange.

### The Anatomy of a Heartbeat Request

A standard heartbeat request contains:

1. **Type**: A single byte indicating request or response
2. **Payload Length**: A 16-bit integer specifying the expected payload size
3. **Payload**: The actual data to be echoed back (variable length)
4. **Padding**: Additional bytes to align the packet

The vulnerability arises because the server blindly trusts the payload length provided by the client. If an attacker sends a payload length of 64KB but only sends a few bytes of actual data, the server will read 64KB of data from its heap memory - including whatever sensitive information resides there.

## The Vulnerable Code Path

```c
/* Vulnerable Code - OpenSSL 1.0.1 (2011-2014) */
int dtls1_process_heartbeat(SSL *s) {
    unsigned char *p = &s->s3->rrec.data[0];
    unsigned short hbtype;
    unsigned int payload_length;
    unsigned char *payload, *bp;
    int r;

    /* Read heartbeat type and length from packet */
    hbtype = *p++;
    n2s(p, payload_length);  /* No validation of payload_length */

    /* Allocate memory for response */
    bp = OPENSSL_malloc(1 + 2 + payload_length + padding);

    /* This copies user-controlled length bytes from memory! */
    memcpy(bp, p, payload_length);  /* Buffer over-read vulnerability */

    /* Send response containing leaked memory */
    dtls1_write_bytes(s, TLS1_RT_HEARTBEAT, bp, 1 + 2 + payload_length + padding);
}
```

In the code above, `payload_length` is read directly from the client's packet with no check that it matches the actual payload size. The `memcpy` call then copies that many bytes from the server's process memory into the response buffer, whether or not those bytes belong to the heartbeat payload.

## Stage 2: Under Attack

The attack exploits this trust by sending a malformed heartbeat request. The attacker claims a payload length of 64KB (the maximum heartbeat size) but only sends a few bytes of data. The vulnerable server, trusting the length field, responds with 64KB of its process memory - potentially containing private keys, session tokens, user credentials, or other sensitive data.

### What an Attacker Could See

The leaked memory could contain:

- **Private TLS keys**, which in some deployments using RSA key exchange could allow previously recorded encrypted traffic to be decrypted.
- **Session cookies** allowing account takeover
- **Passwords** and other credentials
- **Email content** and private messages
- **API keys** and authentication tokens

The attack typically left little or no evidence in standard server logs, making exploitation extremely difficult to detect without specialized monitoring.

## The Race to Disclosure

The vulnerability was discovered independently by security researchers at Codenomicon and Google's security team. After coordinated disclosure to the OpenSSL maintainers, a patch was released on April 7, 2014. However, the patch required affected services to upgrade their OpenSSL implementations, restart their services, and - crucially - revoke and reissue their SSL certificates and session tokens.

The patch was simple but critical:

```c
/* Patched Code - OpenSSL 1.0.1g (April 7, 2014) */
int dtls1_process_heartbeat(SSL *s) {
    unsigned char *p = &s->s3->rrec.data[0];
    unsigned short hbtype;
    unsigned int payload_length;
    unsigned char *payload, *bp;
    int r;

    /* Read heartbeat type and length from packet */
    hbtype = *p++;
    n2s(p, payload_length);

    /* Validate that length doesn't exceed what's available */
    if (1 + 2 + payload_length + 16 > s->s3->rrec.length)
        return 0;  /* Invalid request - drop it */

    payload = &p[0];
    bp = OPENSSL_malloc(1 + 2 + payload_length + padding);

    /* Now this copies only valid payload data */
    memcpy(bp, p, payload_length);

    dtls1_write_bytes(s, TLS1_RT_HEARTBEAT, bp, 1 + 2 + payload_length + padding);
}
```

## Stage 3: The Aftermath

The Heartbleed vulnerability exposed fundamental weaknesses in how the tech industry approached open-source software security. While major services scrambled to patch their systems, the full scope of the damage remained unknown due to the attack's undetectable nature.

### Affected Services

Some of the most popular online services were affected, including:

- Yahoo
- OKCupid
- LastPass
- GitHub
- Stack Overflow
- Various banks and government portals

### The Response

The response to Heartbleed was swift but chaotic. System administrators worldwide worked around the clock to patch servers, revoke compromised certificates, and force password resets. The patch alone wasn't enough - any server that had been vulnerable had potentially been compromised, requiring a comprehensive security audit.

### The Open-Source Paradox

Heartbleed highlighted a critical paradox: OpenSSL was securing the vast majority of the internet's encrypted traffic, yet its maintenance was largely volunteer-driven and critically underfunded. At the time of Heartbleed's disclosure, the OpenSSL project was maintained by only a handful of core developers and operated with extremely limited funding despite protecting a significant portion of the Internet's encrypted communications. The incident highlighted the risks of relying on critical infrastructure that lacked sufficient financial and engineering support.

This led to the formation of the Core Infrastructure Initiative (CII) in April 2014, a collaborative effort backed by major tech companies to provide sustained funding and security auditing for critical open-source infrastructure projects. The CII committed over $5 million in its first year to support OpenSSL and other critical projects.

### Lessons Learned

The Heartbleed vulnerability taught the tech industry several critical lessons:

1. **Security requires validation at every boundary**: Trusting user-supplied values without validation is a recipe for disaster
2. **Memory safety matters**: Memory-safe programming languages such as Rust are designed to prevent this class of memory over-read vulnerability through compile-time safety guarantees
3. **Open-source needs sustainable funding**: Critical infrastructure can't be maintained on goodwill alone
4. **Security audits are essential**: Regular code reviews and fuzzing can catch vulnerabilities before attackers do
5. **Patch alone isn't enough**: When a vulnerability potentially leaked cryptographic keys, certificates must be revoked and reissued

## Historical Timeline

The story of Heartbleed spans from a well-meaning code commit to a global security crisis that reshaped how the tech industry approaches open-source security.

<HeartbleedTimeline client:load />

### Key Events

**December 2011**

- A well-meaning developer commits the heartbeat extension code to OpenSSL, introducing the bounds-check vulnerability that would go unnoticed for over two years.

**April 2014**

- Security researchers at Codenomicon and Google independently discover the vulnerability
- The OpenSSL project is notified and begins work on a patch
- April 7: Disclosure of CVE-2014-0160 sends shockwaves through the internet
- Administrators worldwide race to patch their servers

**April 2014 (Late)**

- The Core Infrastructure Initiative is formed to provide sustainable funding for critical open-source projects
- Major tech companies pledge millions to secure the open-source ecosystem

**2015-Present**

- OpenSSL adopts more rigorous testing and review processes
- The vulnerability serves as a wake-up call for memory-safe programming languages
- TLS 1.3 is developed with improved security properties
