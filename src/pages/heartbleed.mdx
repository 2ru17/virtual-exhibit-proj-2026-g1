# The Heartbleed Bug (CVE-2014-0160)

_When the Internet's heart started bleeding secrets._

On April 7, 2014, the cybersecurity world changed when CVE-2014-0160 was disclosed: a critical flaw in OpenSSL's TLS heartbeat extension that let attackers read up to 64 KB of server memory per request. Private keys, session tokens, passwords, and other sensitive data could leak without leaving clear traces in logs.

Heartbleed is a canonical case study in how a single missing validation check can compromise encrypted communications at Internet scale. This exhibit walks through the vulnerable heartbeat design, shows how the attack worked, and traces the response that followed.

## Stage 1: Healthy Server Heart

The TLS heartbeat extension was designed as a lightweight keep-alive mechanism - a simple "ping" between client and server to maintain an active connection without the overhead of renegotiating cryptographic parameters. In a properly functioning implementation, a client sends a heartbeat request containing a payload and a length field, and the server echoes back exactly what was sent.

The heart pulses rhythmically to simulate a live TLS heartbeat exchange.

### The Anatomy of a Heartbeat Request

A standard heartbeat request contains:

1. **Type**: A single byte indicating request or response
2. **Payload Length**: A 16-bit integer specifying the expected payload size
3. **Payload**: The actual data to be echoed back (variable length)
4. **Padding**: Additional bytes to align the packet

Every field in that request comes straight from the client, and the server is expected to trust it. That trust is exactly what would later go wrong.

## Where the Flaw Lived

Inside OpenSSL's heartbeat handler, the server took the payload length declared in the incoming packet at face value. It allocated a response buffer sized to match that declared length, then copied that same number of bytes out of memory and back into the response - without ever checking whether the client had actually sent that much data in the first place.

That single missing comparison was the entire vulnerability. A well-behaved client's declared length would always match its real payload, so the flaw stayed invisible for years. But nothing stopped a client from lying: declaring a 64 KB payload while sending only a couple of bytes. The server would faithfully copy 64 KB out of its own working memory - most of it never intended for anyone outside the process - and hand it straight back to whoever asked.

## Stage 2: Under Attack

The attack exploits this trust with a single malformed request. The attacker sends a heartbeat tagged with a declared length of 65,536 bytes - the maximum the protocol allows - but includes only a couple of real bytes, say "Hi." The exchange looks deceptively ordinary from the outside: one request goes out, one response comes back. But because the server never checks that the declared length matches what was actually sent, it reads a full 64 KB straight out of its own working memory and returns all of it, private keys and session tokens included, packaged as if it were the legitimate echo the client had asked for.

The user clicks the heart to simulate sending a malformed heartbeat request - one that claims a payload of 64KB but actually sends only a few bytes. Pop-up info cards appear progressively, revealing context about the exploit mechanics.

### What an Attacker Could See

The leaked memory could contain:

- **Private TLS keys**, which in some deployments using RSA key exchange could allow previously recorded encrypted traffic to be decrypted.
- **Session cookies** allowing account takeover
- **Passwords** and other credentials
- **Email content** and private messages
- **API keys** and authentication tokens

The attack typically left little or no evidence in standard server logs, making exploitation extremely difficult to detect without specialized monitoring.

## The Race to Disclosure

The vulnerability was discovered independently by security researchers at Codenomicon and Google's security team. After coordinated disclosure to the OpenSSL maintainers, a patch was released on April 7, 2014. However, the patch required affected services to upgrade their OpenSSL implementations, restart their services, and - crucially - revoke and reissue their SSL certificates and session tokens.

The patch was simple but critical: before doing anything else, the server now compares the declared payload length against the actual size of the data it received. If the declared length is larger than what's really there, the request is dropped outright instead of being processed. That one added check closed the entire hole - the server never again reads or returns memory beyond what the client actually sent.

## Stage 3: The Aftermath

The Heartbleed vulnerability exposed fundamental weaknesses in how the tech industry approached open-source software security. While major services scrambled to patch their systems, the full scope of the damage remained unknown due to the attack's undetectable nature.

### Affected Services

Some of the most popular online services were affected, including:

- Yahoo
- OKCupid
- LastPass
- GitHub
- Stack Overflow
- Various banks and government portals

### The Response

The response to Heartbleed was swift but chaotic. System administrators worldwide worked around the clock to patch servers, revoke compromised certificates, and force password resets. The patch alone wasn't enough - any server that had been vulnerable had potentially been compromised, requiring a comprehensive security audit.

### Lessons Learned

The Heartbleed vulnerability taught the tech industry several critical lessons:

1. **Security requires validation at every boundary**: Trusting user-supplied values without validation is a recipe for disaster
2. **Memory safety matters**: Memory-safe programming languages such as Rust are designed to prevent this class of memory over-read vulnerability through compile-time safety guarantees
3. **Open-source needs sustainable funding**: Critical infrastructure can't be maintained on goodwill alone
4. **Security audits are essential**: Regular code reviews and fuzzing can catch vulnerabilities before attackers do
5. **Patch alone isn't enough**: When a vulnerability potentially leaked cryptographic keys, certificates must be revoked and reissued
